# 02-等待解析

## 目的

讓使用者在提交文件後，能明確知道系統正在處理，而不是面對空白畫面或無限 loading。此階段的重點是穩定的狀態呈現與可中止/離開的能力，確保解析失敗或取消時不會誤判成成功。

## 進入條件

- 使用者已完成文件選擇與上傳
- 後端已接受文件並建立解析任務
- 系統已進入等待解析狀態

## 完成條件

以下任一條件成立時，此流程可視為已進入下一階段：

- 解析成功，並返回欄位結果
- 解析失敗，並顯示錯誤狀態與可重試選項
- 使用者主動取消或離開等待狀態

## 主要行為

### 1. 顯示解析狀態

- 顯示明確狀態標籤，例如：
  - 「上傳成功，正在解析」
  - 「解析中」
  - 「處理中」
- 顯示檔名或任務識別資訊
- 若有處理階段資訊，可顯示目前進度：例如「OCR 中」「欄位抽取中」

### 2. 避免空白等待

- 不得顯示空白頁面、無狀態訊息或單一旋轉動畫而無文字回饋
- 至少提供：
  - 狀態文字
  - 進度或階段資訊
  - 可取消/離開操作

### 3. 解析中取消

- 使用者可在解析期間取消任務
- 若取消成功：
  - 返回到可操作的起始狀態
  - 清除舊任務狀態
  - 不視為成功結果
- 若取消後任務已進入後端處理，需依照實際狀態處理，避免誤判

### 4. 解析失敗

- 若後端回傳解析失敗，前端必須停止 loading
- 顯示失敗原因並提供：
  - 重試
  - 重新選擇文件
  - 返回上一層或開始頁面
- 不得永遠停留在「解析中」

### 5. 解析逾時或等待過久

- 若超出預期等待時間，應顯示超時訊息
- 提供「重新嘗試」或「檢查檔案」等後續動作
- 若在等待期間使用者離開，應能安全撤回/停止此任務

## 必要支線

### 支線 A：解析中取消

- 使用者在解析期間選擇取消
- 系統應立即停止 UI loading
- 任何後續成功回應都需被忽略或明確驗證為已失效

### 支線 B：解析失敗

- 後端回傳失敗訊息
- 前端顯示失敗而非無限等待
- 使用者可重新選擇文件或重試

### 支線 C：解析逾時

- 系統開始計時，若超過容許等待時間
- 顯示逾時警示
- 使用者可選擇繼續等待、重試或更換文件

### 支線 D：後端成功回應晚於取消

- 若取消後才收到成功回應，應視為無效
- 系統需保護不讓已取消任務被誤當完成

## 驗收條件

1. 使用者在上傳後可看到明確的解析中狀態。
2. 解析中畫面不會是空白頁或沒有說明的 loading。
3. 使用者可取消或離開等待狀態。
4. 解析失敗時，不會永久停在 loading。
5. 逾時/長時間等待時，有明確提示與可恢復動作。
6. 取消後，系統不會誤判為成功結果。
7. 成功解析會轉入下一步的結果整理流程。

## 測試

### 1. 正常解析流程測試

- 提交有效文件後
- 期望：顯示「解析中」與檔名資訊
- 在後端成功回應後，進入結果整理畫面

### 2. 取消測試

- 在解析中點擊取消
- 期望：介面回到可操作狀態，且不更新為成功結果

### 3. 失敗測試

- 模擬後端解析失敗
- 期望：顯示錯誤訊息，停止 loading，並提供重試或返回操作

### 4. 逾時測試

- 模擬長時間未回應
- 期望：顯示超時狀態與后續處理選項

### 5. 順序競態測試

- 在取消後再收到成功回應
- 期望：系統忽略為過期結果，並保持取消狀態

## 介面與約束建議

- 狀態文案需簡短、明確且可理解
- 按鈕與提示應明確區分「取消」、「重試」、「返回」
- 解析中可能有多個階段，優先採用可讀的階段名而非純粹動畫
- 若後端沒有進度回饋，前端至少應保留一個基礎狀態與時間資訊

## 交付標準

此階段的最低交付要求是：

- 解析期間有明確狀態
- 使用者可中止或離開
- 失敗與逾時都有明確後續動作
- 不會因為異常回應而誤判任務成功

若以上條件成立，則可進入「解析結果整理」流程。
