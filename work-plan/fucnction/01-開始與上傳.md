# 01-開始與上傳

## 目的

讓使用者在第一步就能安全、清楚地選擇文件，並啟動解析流程。此流程的核心目標是：

- 使用者可以選擇符合格式與大小限制的文件
- 上傳流程有明確狀態與回饋
- 成功後進入解析階段，不會卡在無回應狀態
- 上傳失敗、格式錯誤、未選檔案等情境都能被正確處理

這份 spec 只涵蓋「開始與上傳」這個第一個階段，後續的解析等待、欄位審核、驗證與送出會分別在其他 spec 中處理。

## 進入條件

使用者位於文件解析主流程的起始畫面，且尚未開始任何文件上傳。

前置條件：

- 使用者已進入系統的文件解析入口
- 系統已準備好上傳元件或檔案選擇入口
- 使用者可選擇本機檔案作為解析來源

## 完成條件

使用者完成下列任務後，即視為此流程完成：

- 已選擇有效文件
- 文件已成功上傳至後端
- 系統已進入解析中狀態
- 使用者可清楚看到目前處理進度
- 若上傳失敗或檔案不符合規範，系統已顯示明確錯誤並提供可恢復動作

## 主要行為

### 1. 檔案選擇

- 提供可點選的檔案選擇入口，例如「選擇文件」或拖放區域
- 顯示已選檔案名稱、檔案大小與類型（如 PDF、圖片等）
- 若未選擇文件，則不啟動上傳
- 若檔案類型或大小不符合規範，需在上傳前顯示錯誤訊息，而不是直接失敗

### 2. 檔案驗證

系統在上傳前應至少檢查：

- 是否為空檔案
- 檔案格式是否符合允許範圍
- 檔案大小是否超出限制
- 是否為可解析的文件類型

若驗證失敗，應提供以下資訊：

- 明確說明失敗原因
- 建議可採取的補救方式
- 可重新選擇檔案的操作入口

### 3. 上傳流程

- 使用者點選開始上傳後，系統開始發送文件至後端
- 上傳期間需顯示明確狀態，例如：
  - 「上傳中」
  - 「已接收，準備解析」
  - 「解析中」
- 系統不得讓使用者面對空白畫面或無狀態的等待畫面
- 上傳成功後，應建立對應的解析任務並跳轉至下一階段：等待解析

### 4. 成功結果

當上傳成功時，應保留以下資訊：

- 檔名
- 上傳時間或任務建立時間
- 目前狀態：解析中
- 可取消或離開當前流程的入口

### 5. 失敗處理

當上傳因以下因素失敗時，需提供恢復能力：

- 網路中斷
- 後端回應錯誤
- 檔案不符規範
- 上傳服務暫時不可用

失敗時的介面應能讓使用者：

- 重新選擇文件
- 重試上傳
- 返回到可操作狀態，而不是卡在錯誤畫面

## 必要支線

### 支線 A：未選擇文件

- 使用者點擊開始上傳但未選擇任何檔案
- 系統應顯示「請先選擇文件」之類的錯誤訊息
- 不允許執行空請求

### 支線 B：檔案格式或大小不符合預期

- 系統應在選擇檔案後或提交前立即顯示驗證錯誤
- 錯誤訊息需說明允許範圍
- 使用者可以選擇其他檔案繼續

### 支線 C：上傳失敗

- 系統需明確提示失敗原因
- 必須保留重試與重新選擇的能力
- 不應誤導使用者認為任務已成功進入解析

### 支線 D：多次重試

- 使用者可重試上傳，且每次盡量從乾淨狀態重新開始
- 若重試前已有舊錯誤，舊狀態應被覆蓋或清除
- 避免重複提交造成重複任務

## 驗收條件

本流程通過條件如下：

1. 使用者可選擇文件並看到檔名與狀態。
2. 未選擇文件時，不會發送上傳請求。
3. 非法格式或超大檔案時，會顯示明確錯誤訊息。
4. 上傳成功後，畫面會顯示「解析中」或等價狀態。
5. 上傳失敗時，畫面不會永遠停在 loading。
6. 使用者可以在解析前後重新選擇或重試。
7. 流程有明確進入下一步的轉場，且不出現空白畫面。
8. 若後端拒絕上傳，前端仍保持可操作狀態供修正。

## 測試

### 1. 正常流程測試

- 已選擇有效文件後，點擊上傳
- 期望：顯示上傳中狀態
- 後端成功回應後，進入解析中狀態
- 期望：可看到檔名與進度說明，下一步已開始

### 2. 未選擇文件測試

- 不選檔案直接點擊開始上傳
- 期望：不發送請求，顯示請選擇文件的提示

### 3. 檔案驗證測試

- 送入不支援格式或超大檔案
- 期望：在前端阻止上傳，並顯示明確錯誤訊息

### 4. 上傳失敗測試

- 模擬後端回應 4xx / 5xx / 網路錯誤
- 期望：畫面回到可操作狀態，顯示錯誤，且可重試

### 5. 重試測試

- 先失敗，再重新選擇另一個合法文件
- 期望：系統能從錯誤狀態恢復正常，且不混淆舊任務狀態

### 6. UI 狀態測試

- 確認在上傳過程中使用者不會看到空白畫面
- 期望：至少有明確訊息與可中止/離開的入口

## 介面與約束建議

作為第一版設計，建議遵守以下限制：

- 先只支援單一檔案上傳
- 先只處理主要文件格式，避免過度擴大驗證邏輯
- 狀態文案需簡短且明確，避免模糊的「處理中」不配合進度
- 錯誤訊息應以行動導向方式呈現，例如「請重新選擇文件」或「重試」

## 交付標準

此 spec 視為第一版最小可交付範圍，關鍵要求是：

- 啟動流程簡單明確
- 給出可理解的狀態
- 可處理錯誤與重試
- 成功後能正確進入下一個流程

若上述功能皆成立，則可進入下一階段的解析等待流程設計。
