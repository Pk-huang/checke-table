# Checktable

文件解析與欄位審核前端實作。使用者可以選擇一份或多份文件，等待後端逐步解析，再在審核工作區確認、修改與補齊欄位。

後端是題目提供的 mock service，不會真的解析文件，只會回傳假資料。`server.py` 沒有修改；前端則透過 `docker-compose.yml` 加入同一個啟動流程。

## 快速開始

```bash
docker compose up
```

開啟前端：<http://localhost:5173>

後端 API：<http://localhost:8000>

停止服務：

```bash
docker compose down
```

也可以只啟動前端開發環境：

```bash
cd frontend
npm install
npm run dev
```

前端 Vite 開發伺服器會把 `/api` proxy 到 `http://api:8000`（Docker）或設定的 API 位址。

## 已完成的功能

### 上傳與解析

- 可一次選擇多份 PDF、PNG、JPG 文件。
- 逐一呼叫 `POST /api/documents` 上傳文件。
- 透過 SSE 接收 `stage`、`field`、`done`、`error` 事件。
- 顯示目前解析階段、進度、已收到的欄位數與預估剩餘時間。
- 解析中可以取消，取消後忽略晚到的欄位與完成事件。
- 解析失敗時停止 loading，顯示錯誤並提供重新解析操作。

### 審核工作區

- 欄位依「基本資料、營養標示、檢驗結果、廠商資訊」分組。
- 同一群組內保留後端回傳的相對順序。
- 可展開或收合群組，並依全部、缺漏、低信心、已完成篩選欄位。
- 欄位可以直接編輯。
- `confidence < 0.7` 顯示「建議檢查」。這個門檻是前端第一版的暫定值。
- 多候選欄位可以選擇候選值，也可以切換為自訂輸入。
- 品名、有效日期、廠商名稱為必填欄位，缺漏時會阻擋確認操作。
- 支援淺色與深色介面。

目前的「確認送出」只代表前端審核流程完成，會進入完成畫面；題目提供的後端沒有正式送出 endpoint，因此尚未真正提交資料。

## 設計判斷

### 題目指定：參考介面最嚴重的三個問題

> 這張圖你覺得最嚴重的三個問題是什麼？為什麼？你自己的版本怎麼處理？

1. **資訊被平均塞在同一列。** 欄位名稱、值、信心度、狀態、候選值與頁碼同時競爭注意力，會讓使用者難以快速找到真正需要修改的值。這版把欄位值與編輯操作放在主要視覺位置，頁碼和警示放在輔助資訊。
2. **風險狀態不夠明確。** 低信心欄位和法規必填缺漏會直接影響送出結果，因此這版使用「建議檢查」、缺漏提示與確認按鈕禁用，讓使用者先處理高風險欄位。
3. **欄位數量增加後難以掃描。** 需求提到可能有上百個欄位，因此這版加入群組折疊、分類篩選、狀態篩選與各群組數量，讓使用者可以先縮小範圍，再逐筆檢查。

### 題目 2：這個介面上，你決定不顯示或降級顯示哪些資訊？為什麼？

- 信心度沒有用精確數字佔據每一列，而是先轉成「建議檢查」狀態；使用者的第一個任務是找到需要人工確認的欄位，不是比較所有小數差異。
- 頁碼保留在欄位輔助資訊中，但目前沒有 PDF 預覽、原文定位或文字高亮，因此頁碼只能作為回看文件時的提示。
- 後端事件與 document ID 不直接顯示在畫面上，避免把除錯資訊混入審核流程。

### 題目 3：這幾條需求裡，你覺得有哪兩條互相衝突？你怎麼取捨的？

- **資訊完整性與大量欄位的可掃描性衝突：** 保留會影響決策的值、必填狀態、低信心狀態與頁碼，其餘細節透過展開、篩選或後續來源預覽處理。
- **解析完整性與取消操作衝突：** 使用者按下取消後優先尊重取消意圖，立即離開解析畫面，並以 `AbortController` 和 task ID 忽略晚到事件，不讓舊任務把畫面誤切到審核頁。

### 題目 1：這份需求哪裡沒講清楚？你是怎麼假設的？

- 一次選取的文件會依序上傳與解析，欄位暫時合併到同一個審核工作區。
- `value.trim() === ''` 代表欄位缺漏。
- `confidence === null` 代表後端沒有抽到該欄位的可信度；這類欄位仍需人工確認。
- 品名、有效日期、廠商名稱由後端標為 `required: true`，前端依此驗證，而不是只用 label 判斷。
- 暫時接受題目 mock service 的檔案限制與資料格式，正式產品仍需明確的檔案大小、格式與權限規則。

目前測試保護的重點包括：

- 上傳 API 的 `FormData` 傳遞與 response 欄位轉換。
- 上傳失敗時的錯誤處理。

### 手動驗證

使用 `docker compose up` 後，在 `http://localhost:5173` 測試：

| 情境 | 測試方式 | 預期結果 |
|---|---|---|
| 預設流程 | 選擇文件並開始解析 | 上傳、解析、審核畫面依序出現 |
| 多檔流程 | 一次選擇兩份以上文件 | 文件依序上傳與解析，欄位進入審核工作區 |
| 解析失敗 | 開啟 `http://localhost:5173/?fail_at=3` | 顯示錯誤，不會永久停在 loading，可重新解析 |
| 大量欄位 | 開啟 `http://localhost:5173/?field_count=120` 或 `?field_count=300` | 可透過群組與篩選操作欄位 |
| 放慢解析 | 開啟 `http://localhost:5173/?speed=0.1` | 可觀察進度並按取消 |
| 必填驗證 | 清空品名、有效日期或廠商名稱 | 確認按鈕 disabled，並顯示待補數量 |
| 多候選 | 選候選值，再切換自訂輸入 | 可以選擇候選值或輸入自己的值 |
| 取消競態 | 解析中按「取消並返回」 | 回到上傳頁，不會因晚到事件誤進審核 |

後端健康檢查：

```bash
curl http://localhost:8000/api/health
```

目前沒有完整的瀏覽器 E2E 測試；多檔流程與互動狀態主要透過手動驗證。解析失敗已用 `fail_at=3` 手動確認會停止 loading 並提供重試，但尚未有元件測試保護這條流程，因此這是目前測試覆蓋的缺口。

## 未完成與後續方向

- **正式送出 API：** 題目後端未提供送出 endpoint，因此目前只完成前端確認畫面。
- **逐欄確認狀態：** 目前支援編輯欄位，並在頁面底部進行整體確認；尚未提供每個欄位獨立的「已確認」狀態或逐欄確認操作。這是對「欄位能確認、修改」中確認語意的簡化。
- **文件來源關聯：** 多檔欄位目前合併在同一個工作區，審核頁尚未逐欄顯示來源文件。正式版本需要以 document ID 與欄位 ID 建立穩定識別，避免不同文件的欄位 ID 重複造成編輯歧義。
- **PDF 預覽與來源高亮：** 需要後端提供欄位座標或文字範圍後才能可靠實作。
- **虛擬列表：** 目前已用 120 與 300 欄位手動驗證群組與篩選操作，但尚未加入 virtualization。
- **解析失敗的自動測試：** `fail_at=3` 已手動驗證錯誤畫面與重試流程，但尚未補元件或 E2E 測試，因此目前只完成行為，尚未完成自動化保護。
- **拖放上傳：** 目前畫面保留拖放提示，但實際上傳入口是檔案選擇器，拖放事件尚未補上。
- **草稿保存與恢復、解析逾時、完整檔案大小驗證、完整無障礙與跨裝置測試：** 列為後續工作。

## API 摘要

### 上傳文件

```text
POST /api/documents
Content-Type: multipart/form-data
欄位名稱：file
```

回應：

```json
{ "document_id": "b74bacee-...", "filename": "report.pdf" }
```

### 解析文件

```text
GET /api/documents/{document_id}/extract
```

回傳 `text/event-stream`，包含：

- `stage`：解析階段與 progress。
- `field`：單筆抽取欄位。
- `done`：該文件解析完成。
- `error`：解析途中失敗。

測試用 query 參數：

| 參數 | 說明 |
|---|---|
| `field_count` | 欄位數量，可設 1～300，預設 18 |
| `speed` | 速度倍率，預設 1.0，下限 0.1 |
| `fail_at` | 從 0 起算，在指定欄位後回傳錯誤；`-1` 表示停用 |

例如：

```text
/api/documents/{id}/extract?field_count=120&speed=5
/api/documents/{id}/extract?fail_at=3
```

其他 endpoint：`GET /api/health`。服務重啟後，既有的 `document_id` 會失效。
